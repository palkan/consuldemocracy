# Notes for coding agents

## Type checking with Sorbet

The Ruby code in `app/` and `lib/` is type checked with [Sorbet](https://sorbet.org).
Signatures use the regular Sorbet syntax (`sig { ... }`). `sorbet-runtime` also checks
them while the code runs in the development and test environments, so the test suite
fails when a signature is wrong. In production, signatures aren't checked at runtime.

### Commands

```sh
bin/srb tc                          # Type check the project (less than a second); must print "No errors! Great job."
bin/tapioca dsl                     # Regenerate the RBIs of Rails' generated methods (needs the database)
bin/tapioca dsl Budget::Investment  # Regenerate the RBI of one constant
bin/tapioca dsl --verify            # Check that the generated RBIs are up to date
bin/tapioca gems                    # Regenerate the gem RBIs after changes to Gemfile.lock
bin/tapioca annotations             # Update the community RBIs (rbi-central)
bundle exec spoom srb coverage      # Show the sigil and signature coverage
```

`bin/srb tc` checks the whole project; to see the errors in one file, filter the output
(`bin/srb tc 2>&1 | grep app/models/user.rb`). Run it after every change to Ruby code.
CI runs it in the linters workflow.

### Files

| Location | Content | Edit by hand? |
|---|---|---|
| `sorbet/config` | Sorbet options and ignored paths | Yes |
| `sorbet/rbi/gems/` | Gem RBIs, generated by `bin/tapioca gems` | No |
| `sorbet/rbi/annotations/` | Community RBIs, generated by `bin/tapioca annotations` | No |
| `sorbet/rbi/dsl/` | RBIs of methods that Rails generates (columns, associations, scopes, routes, mailers...), generated by `bin/tapioca dsl` | No |
| `sorbet/rbi/shims/` | Declarations that Tapioca can't generate (see below) | Yes |
| `sorbet/tapioca/compilers/` | Custom Tapioca DSL compilers | Yes |
| `sorbet/tapioca/require.rb` | Lazily loaded gem files that `bin/tapioca gems` must load | Yes |
| `sorbet/tapioca/config.yml` | Tapioca options (it loads the app in the test environment) | Yes |
| `config/initializers/00_sorbet.rb` | Runtime configuration of `sorbet-runtime` | Yes |

Never edit generated RBIs. When a generated RBI is wrong or incomplete, add a shim or a
Tapioca compiler.

### Rules for new and changed code

- Every Ruby file in `app/` and `lib/` starts with a sigil. Use `# typed: strict` for new files.
  `# typed: true` is fine for controllers, mailers and other classes that assign many instance
  variables outside `initialize`. Don't use `# typed: false` or `# typed: ignore`.
- Every method has a signature. Prefer precise types; use `T.untyped` only when the type really
  can be anything (for example, values that specs replace with doubles), and `T.unsafe` only as
  the last resort.
- Classes that inherit from `ApplicationRecord`, `ApplicationController`, `ApplicationComponent`
  and `ApplicationMailer` already have `extend T::Sig`. Other classes and all modules need
  `extend T::Sig` before the first `sig`.
- After changes to associations, scopes, enums, columns (migrations), routes, mailers or
  concerns, run `bin/tapioca dsl` and commit the changed RBIs.
- After changes to `Gemfile.lock`, run `bin/tapioca gems` and commit the changed RBIs.

### Signatures

```ruby
sig { params(user: User, limit: Integer).returns(T::Array[Proposal]) }
def recommended_proposals(user, limit: 3)

sig { returns(T::Boolean) }
def published?

sig { void } # Controller actions, callbacks and methods whose return value isn't used
def index
```

`sorbet-runtime` raises a `TypeError` in development and test when a value doesn't match the
signature, so check what the code really returns:

- `T::Boolean` only accepts `true` and `false`. `foo && bar` can return `nil` or another object.
- `T.bind`, `T.cast` and `T.let` are checked at runtime too. Don't use `T.bind(self, Model)` in a
  lambda that also runs on another class. For example, Globalizable copies the conditions of
  `validates_translation` to `Model::Translation`; use `->(record) { record.foo }` there.
- Specs that pass doubles or dummy classes fail with precise types. Use `T.untyped` for these
  parameters, or `T::Sig::WithoutRuntime.sig` for a signature that only Sorbet checks.
- Type aliases (`Recommendations = T.type_alias { ... }`) are real constants. Don't give them
  the name of an existing namespace: a `Proposals` alias in a component breaks
  `Proposals::GeozonesComponent` in its template.
- A method that overrides a method with a signature needs `override`. A module method that an
  includer replaces with a different signature needs `overridable` in the module and
  `override(allow_incompatible: true)` in the includer.

### Active Record

Tapioca generates `Model::PrivateRelation` (`Model.where(...)`),
`Model::PrivateAssociationRelation` (`record.models.where(...)`) and
`Model::PrivateCollectionProxy` (`record.models`). They don't exist in Rails, but
`config/initializers/00_sorbet.rb` defines them as aliases of the classes that Rails generates,
so signatures can use them. A class method that is also called on associations returns
different classes, so use a union:

```ruby
sig { returns(T.any(Proposal::PrivateRelation, Proposal::PrivateAssociationRelation)) }
def self.featured
```

Relations delegate missing methods to the model class (`Proposal.published.search(terms)`).
The custom `RelationClassMethods` compiler declares the class methods that are defined in
`app/` and have a signature on the relation types. When a concern's class method returns
`ActiveRecord::Relation`, the compiler declares that it returns the model's relation type.

Tapioca types nullable columns and all associations as `T.nilable(...)`
(`belongs_to_required_by_default` is `false` in this app). Handle `nil`, or use `T.must`
when the value can't be `nil` there. Assign to a local variable to narrow a type:
`if (author = proposal.author)`.

### Concerns and modules

Declare the class that a module needs with `requires_ancestor`:

```ruby
module Flaggable
  extend ActiveSupport::Concern
  extend T::Helpers
  extend T::Sig

  requires_ancestor { ApplicationRecord }
```

- View helpers (`app/helpers/`) require `ActionView::Base`. Helpers that components include
  (`GlobalizeHelper`, `TranslatableFormHelper`) require `ActionView::Helpers`, because
  `ViewComponent::Base` doesn't inherit from `ActionView::Base`.
- Controller concerns require `ActionController::Base` (or `ApplicationController`).
- Component concerns require `ApplicationComponent`.
- Methods that every includer must define are `abstract` (`abstract!` in the module,
  `sig { abstract.returns(...) }`, and `override` in the includers). Methods that includers get
  from columns, associations or macros are declared in `sorbet/rbi/shims/app.rbi`.
- Define class methods in `module ClassMethods`, not in `class_methods do ... end` or with
  `def self.method` in `included do ... end`: Sorbet doesn't see methods defined in blocks. The
  custom `ConcernClassMethods` compiler declares `mixes_in_class_methods(ClassMethods)` for every
  module in `app/` that has a `ClassMethods` module.
- Sorbet doesn't see `include` calls in `included do ... end` blocks either. Put them in the
  module body.

### Instance variables

In `typed: strict` files, Sorbet infers the type of an instance variable that `initialize`
assigns from a parameter with a signature. Declare the others with `T.let`:

```ruby
sig { params(proposal: Proposal).void }
def initialize(proposal)
  @proposal = proposal
  @votes = T.let(nil, T.nilable(T::Array[Vote]))
end
```

### Shims

| File | Content |
|---|---|
| `sorbet/rbi/shims/app.rbi` | Methods of the app's classes that Sorbet can't see: methods that concerns expect from includers, methods defined with `define_method`, mixins added by macros (`acts_as_votable`, `pg_search_scope`...) |
| `sorbet/rbi/shims/rails.rbi` | Rails methods missing from the RBIs, and methods that `config/application.rb` and `config/initializers/` add to Rails classes |
| `sorbet/rbi/shims/gems.rbi` | Methods that gems define at runtime, and gem extensions in `config/initializers/` |
| `sorbet/rbi/shims/devise.rbi` | Devise helpers (`current_user`...), Devise controllers and the Devise modules of `User` |
| `sorbet/rbi/shims/foundation_rails_helper.rbi` | The form builder vendored in `vendor/foundation_rails_helper` |

A method in a shim replaces the declaration in the gem RBI, so don't redeclare methods that
already exist (search `sorbet/rbi/` first).

### Known limitations

- Sorbet doesn't type check ERB templates. Components and helpers are checked, but the code
  in `*.html.erb` files isn't.
- Sorbet doesn't support dynamic constants (`"Foo::#{name}".constantize`), splats of arrays with
  an unknown size, or signatures for methods with `(...)` parameters. Rewrite the code with
  explicit parameters, or use `T.unsafe(receiver).method(*args)` as the last resort.
- `--ignore` patterns in `sorbet/config` match any part of a path. Start them with `/` to match
  from the project root.
